# 残留锁恢复设计（草案，不是可执行授权）

目标：故障后可恢复，不以TTL/PID猜测取代排他。适用于未来专用受控根；当前只定义流程，不对任何锁/介质删除、移动或恢复。

## 安全默认

- 残留锁、未知提交或保护失败一律停止写入，显示固定诊断，不暴露路径/原件内容。
- 无自动抢锁、不新增“强制解锁”在线API；SDK close完成也不能证明其他Host已停。
- 活进程持有写句柄时，不得修改锁。只停Notebook请求入口不能作为全体写者已停的证据。

## 运维离线流程

1. 明确专用介质所有者、版本、根目录和全部可能写者范围。未知共享挂载/网络文件系统不进入恢复流程。
2. 用户单独批准停用/完整退出相关写进程，并保存全部草稿；不能根据PID不存在、mtime超时判定安全。逐一记录受控写者停止证据。无法证明全部停止则不恢复。
3. 在只读离线模式保护锁原字节与介质原字节，使用独立命名副本、hash、文件与目录sync；保护失败即中止，不解锁、不初始化空库。
4. 对候选介质执行版本/完整Schema/关联/收据/限额校验。未知提交优先核验持久化收据，不能再次执行原修改来“试试”。坏介质只从明确确认的可用备份生成新候选。
5. 用户确认恢复点与数据损失预览。保留旧介质和旧锁证据，再在全体写者离线条件下通过恢复工具发布新介质/新代际，废弃旧请求作用域；不得手工热删锁后直接继续写。
6. 恢复工具创建全新排他锁并核验候选重开完整一致后，释放自身锁；任一步骤耐久不确定保留保护状态。
7. 用户另行批准重新启用/启动；单写者重新获取，核验只读诊断、库代际和Notebook计数，无误后再允许修改。

## 写锁释放协议决策门禁（Goal Round45，设计而非可执行流程）

以下为当前测试守卫和完整worker的**风险状态矩阵**，`CLOSE_FAILED`是固定诊断，不是锁状态；既有[合成故障回归](<../../tests/unit/medium-guard.test.js>)与[完整worker回归](<../../tests/runtime/worker-ownership.test.js>)证明最后两行的关键区别。文件存在性仅描述进程可见瞬时状态，不证明掉电后目录项持久。

| 故障/阶段 | 旧worker能否仍接收写 | 锁目录项与新写者 | 唯一安全结论 |
|---|---|---|---|
| SDK提交/close失败，尚未执行release | 宿主父侧应立即停写；SDK状态未知 | 当前进程观察残留锁通常拒绝新写者 | 保持隔离，先核验旧worker/其他写者退出；不按错误码或PID自动解锁。 |
| `checkOwner`或`unlink`前失败 | 旧worker可能仍活着 | 可能仍有原锁或被其它进程替换 | 不修改任何锁/介质，人工查明身份。 |
| `unlink`成功，但目录sync前worker崩溃/同步失败 | 即使已停止接单，也可能仍活着；跨Host事实未知 | 锁名**可能已消失**，新写者可`wx`；重启后目录项又可能回归 | 必须返回未知/冻结业务；不能让父侧仅凭`CLOSE_FAILED`或exit 0重启另一写者。 |
| sync完成且close返回成功 | 本worker按本地队列已停止写 | 锁名可能已消失，可由新写者获取 | **仅对本worker的受控正常关闭**成立；其它Host、同UID替换、网络介质均未证明。 |

**明确否决的快捷修复：**只把`fsync`挪到`unlink`之前不能保证删除持久；在unlink后把同名锁重新建立可能与已经进入的新写者并发；根据mtime/PID或异常字符串热删锁会转移所有权；等待worker exit 0不能证明所有可能写者已退出。生产正确性要求跨进程/崩溃一致的单写者协议和强制栅栏，或者始终离线恢复且不能保证可用性。Node路径名`wx`锁加一次目录sync不提供所需的原子交接/防旧代际写入证明。

**候选路线与采纳前置：**A）默认保留残留锁、不提供在线交接；每次受控停机后仍需用户批准全体写者离线核验、保护原件与锁证据、离线恢复、重新授权启动。安全优先但正常重启体验不可接受，不能暗中作为生产方案。B）评估宿主可用的稳定根、强制排他机制及可核验的持久代际栅栏；新写者必须在提交前验证代际且旧写者不能在失去所有权后继续提交，需覆盖unlink两侧SIGKILL、fsync/ENOSPC、重启/双进程、别名/网络文件系统。只在隔离合成介质通过后，经新的宿主Config和运行状态授权再考虑部署实验Bundle。C）若宿主或平台不能提供这些能力，Step 3维持阻断，不改用裸主文件/第二json/默认乐观双写，也不提前制作保存UI。

**路线A最小隔离可行性实测（Goal Round49）：**[工作区测试守卫](<../../tests/fixtures/medium-guard.js>)显式`retainLockOnClose`选项在核对所有者后**不调用unlink**、固定返回`OFFLINE_RECOVERY_REQUIRED`，close路径冻结该句柄；[测试](<../../tests/unit/medium-guard.test.js>)证实本次运行的新写者仍`WRITER_EXISTS`、重试不自动放锁，[完整worker父控制器](<../../tests/runtime/worker-parent.test.js>)证实其关闭报`CLOSE_FAILED`且不允许同父自动restart。**这不是安全的生产自动重启方案**：正常关闭即留下不可自动使用的库，完整离线恢复工具/授权/停进程证据不存在；路径替换、文件系统掉电和同UID对手也未获得证明。默认正常释放分支仍有此前的unlink后sync窗口，正式包完全未改；不得启用此选项声称Step3已验收。

此节不授权删除任何现有测试锁或用户锁，不是用户可执行恢复教程。Step 0–2当前Desktop认证/路由/监听器缺口及上次拒绝额外禁用/恢复的选择仍有效。

## 本地运行时强制排他能力调查（Goal Round50）

在当前隔离运行进程的 Node v24.19.0 / macOS darwin 上只读检查 `node:fs/promises` FileHandle：`sync`/`stat`/`read` 存在，`lock`/`flock` 均不存在；`O_EXCL`、`O_NOFOLLOW` 可用。**这只证实当前 Node 标准 API 没有可直接使用的强制跨进程文件锁接口**，不证明目标 Desktop 所有平台版本的 API，也不排除需要另行审查/批准的宿主原生服务或其他依赖。`wx`/`O_EXCL` 是一次创建竞争，不会自动对旧进程施加提交栅栏；`O_NOFOLLOW` 只约束单次路径打开，不能使父目录替换与先检查后unlink原子。Node `FileHandle.sync` 存在也不等于文件系统/掉电语义已通过。

| 路线 | 额外前置与可行性证据 | 目前决议 |
|---|---|---|
| A：关闭保留锁，恢复一律离线人工 | 用户明确接受正常关闭后无自动重启、批准停写/离线恢复，编写保护/恢复工具且通过crash/ENOSPC矩阵 | 仅隔离证据；不默认启用，不发布。 |
| B：跨进程可自动交接 | 需宿主公开稳定受控根与可靠强制排他/持久代际栅栏；确定平台矩阵和依赖审批，双进程/掉电/路径替换实验 | 当前 Node 原生 FileHandle 接口不能直接实现；不自行安装native包或改Host。 |
| C：维持只读Spike | 不新增生产根、依赖或恢复工具，Desktop Step0–2留待逐次授权补证 | 保持当前安全状态，直到A/B被明确选择并得到证据。 |

用户在Goal Round51**仅选择继续研究路线B**，并明确维持暂不授权Desktop Bundle禁用/恢复；没有授权安装依赖/Bundle或生产介质。真实SDK `writeAtomic` 在tmp+file sync后`rename`覆盖目标，再sync目录。[离线交错证明](<../../tests/unit/fence-check-window.test.js>)在测试接缝将“读取代际1”与原始SDK `rename`隔开：新写者提交代际2与完整`new`，旧写者仍把目标覆盖为`old`。这是一次代际检查无法替代原子栅栏的反例，并不否定真正可强制互斥的未来实现。

路线B下一技术准入：确认独立且受控的稳定介质与Host可用公开能力；找到能将**代际验证与实际发布动作原子绑定**或能强制排除旧写者发布的原语，并在已许可平台矩阵测试进程崩溃/同步失败/目录替换。当前没有此原语的已证合同，不往现有SDK外层再加一次读锁或仅在消息队列检查代际伪装安全；不以复制Snapshot到另一写者进程替代原子所有权。每次运行状态变更仍单独取得授权。

## 发布前仍缺

- 离线恢复工具、严格所有权/路径安全、锁证据保护及未知提交核验测试。
- 恢复过程中SIGKILL/ENOSPC/fsync拒绝矩阵；旧锁与新代际不得混用。
- 用户可操作指引与实机停启验收。此文档不能当作恢复成功证据。
